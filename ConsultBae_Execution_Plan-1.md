# ConsultBae AI Automation Assignment — Execution Plan

## 0. Purpose

This document defines the implementation workflow for the ConsultBae assignment.

The goal is to build a repeatable, auditable and extensible data-processing pipeline using PostgreSQL as the canonical database.

The pipeline must:
- ingest all three source CSVs;
- preserve raw source data;
- detect structural and data-quality problems;
- normalize values according to common canonical rules;
- validate semantic correctness;
- resolve the same worker across multiple source systems;
- generate a global `WorkerID`;
- populate the canonical worker/profile tables;
- maintain auditability and security;
- support future expansion and Task 3 audio submissions.

# 3. Canonical Data Rules

These rules must be established before modifying the source files.

## 3.1 WorkerID

- Generated by our system.
- Global identifier.
- Unique.
- Immutable.
- Not taken directly from any source CSV.
- Used as the relationship key between tables.

Example:

```text
W000001
W000002
W000003
```

## 3.2 Worker Name

Canonical format:

```text
Aa / Title Case
```

Examples:

```text
RAHUL CHOPRA -> Rahul Chopra
ritu sharma  -> Ritu Sharma
 Ritu SHARMA -> Ritu Sharma
```

Rules:
- trim leading/trailing whitespace;
- collapse unnecessary multiple spaces;
- normalize capitalization;
- preserve meaningful punctuation where possible;
- never use name as the primary key.

## 3.3 Email

Canonical format:

```text
lowercase + trimmed
```

Example:

```text
ISHA.CHOPRA95@MAILTEST.EXAMPLE.ORG
        ->
isha.chopra95@mailtest.example.org
```

Rules:
- trim;
- lowercase;
- validate basic email syntax;
- retain source value for audit when transformed.

Test/placeholder domains are not automatically invalid solely because they are synthetic-looking.

## 3.4 Phone Number

Canonical representation:

```text
exactly 10 digits
```

Examples:

```text
+91-9000000295 -> 9000000295
919000000295   -> 9000000295
09000000295    -> 9000000295
9000000295     -> 9000000295
```

Rules:
- normalize country-code/prefix variations;
- remove formatting characters only when the resulting number is valid;
- final canonical value must contain exactly 10 digits;
- invalid/unresolvable phone numbers are quarantined or flagged.

## 3.5 Location

Stage 1:
- trim;
- collapse whitespace;
- normalize capitalization.

Stage 2:
- apply controlled alias mapping.

Examples:

```text
PUNE -> Pune
pune -> Pune
Bangalore -> Bengaluru
Gurgaon -> Gurugram
```

Do not automatically merge geographically related values such as `Delhi`, `New Delhi` and `Delhi NCR` unless a business rule explicitly permits it.

## 3.6 Skills

Normalize and consolidate skills.

Rules:
- trim each skill;
- normalize capitalization;
- remove duplicates;
- preserve meaningful multi-word skills;
- combine skills from trusted source records when the same worker is resolved.

Example:

```text
" python, React, python, MongoDB "
        ->
"Python, React, MongoDB"
```

For this assignment, skills can remain in the Worker Identity table as a normalized consolidated field. A separate Skill entity can be introduced later if advanced skill management becomes necessary.

## 3.7 Work Experience

Canonical type:

```text
DECIMAL
```

Unit:

```text
years
```

Do not store `"4.2 years"` as free text in the canonical table.

## 3.8 CTC

Canonical database unit:

```text
INR
```

Target field:

```text
current_ctc_inr
```

The source data contains mixed representations, including decimal values that appear to represent LPA and absolute numeric INR-like values.

Example normalization:

```text
4.2 -> 420000 INR
```

The interpretation rule must be documented and the original source value retained for auditability.

## 3.9 Applied Date

Canonical database format:

```text
YYYY-MM-DD
```

Observed source formats include:

```text
DD-MM-YYYY
YYYY-MM-DD
MM/DD/YYYY
DD Mon YYYY
```

Parsing must be source-aware. Do not blindly depend on a generic date parser for ambiguous values.

## 3.10 Gig Rate

Do not store mixed units in one string.

Use:

```text
rate_amount
rate_unit
```

Examples:

```text
1415/hr
->
rate_amount = 1415
rate_unit = HOUR
```

```text
15k/month
->
rate_amount = 15000
rate_unit = MONTH
```

## 3.11 Status

Canonical allowed values:

```text
ACTIVE
INACTIVE
PAUSED
```

Case differences are normalized.

Unknown values are not guessed.

## 3.12 Verified

Canonical database type:

```text
BOOLEAN
```

Mapping:

```text
Y / Yes / yes / YES -> TRUE
N / No / no / NO     -> FALSE
```

Unknown values are flagged.

## 3.13 Projects Completed

Canonical type:

```text
INTEGER
```

Validation:

```text
integer >= 0
```

# 4. Data Classification Rules

Every record/field should fall into one of these outcomes:

```text
VALID
WARNING
REPAIRABLE
REJECTED
FATAL
```

**VALID:** no problem.

**WARNING:** valid data that required a safe normalization, e.g. `PUNE -> Pune`.

**REPAIRABLE:** a known deterministic corruption can be safely fixed, e.g. repeated header row.

**REJECTED:** the record cannot be safely interpreted.

**FATAL:** a pipeline-level problem prevents safe processing, e.g. database unavailable.

# 15. STEP 9 — Entity Resolution

Goal:

```text

      |
      v
Does Worker already exist?
     /    YES  NO
    |    |
```

Matching hierarchy:

1. Exact normalized email.
2. Exact normalized phone.
3. Strong combinations such as name + phone, name + email, name + phone + location.


# 30. Scalability Strategy

Important principles:

### Batch processing

Process records in batches instead of loading everything into application memory.

### Database indexes

Index fields used for entity matching:

```text
normalized email
normalized phone
WorkerID
source identifiers
```

### Transactions

Use transactions for atomic core writes.

### Idempotency

Use import batches and source-record identity.

### Raw/staging/core separation

Do not contaminate canonical data with raw source corruption.

### Modular processing

Keep:

```text
ingestion
normalization
validation
matching
transformation
database
```

as separate modules.

### Future source systems

A fourth source should be able to enter through:

```text
new adapter
   |
same canonical rules
   |
same entity-resolution system
   |
same WorkerID
```

| Uppercase name | Normalized |
| Uppercase email | Lowercased |

| Blank row | Skipped/rejected + audited |
| Invalid status | Rejected/quarantined |
| Y/Yes | TRUE |
| N/No | FALSE |
| Mixed CTC | Canonical INR |
| Mixed date format | Canonical DATE |
| Same person across files | Same WorkerID |
| Same name, different person | Not automatically merged |
| Same file twice | No duplicate workers |
| DB failure | Transaction rollback |
| Invalid record | Quarantine |
| Future new source | Existing architecture remains usable |

# 33. Golden Rules

1. Never modify raw source data.
2. Never insert raw data directly into core tables.
3. Normalize before entity resolution.
4. WorkerID is the global relationship key.
5. WorkerName is readable data, not a foreign key.
6. Never merge workers using name alone.
7. Preserve source provenance.
8. Record every automatic correction.
9. Quarantine data that cannot be safely repaired.
10. Use database transactions for canonical writes.
11. Keep secrets out of Git.
12. Do not expose unnecessary PII in logs.
13. Make ingestion idempotent.
14. Test every layer independently before moving forward.
15. Do not optimize for scale before correctness, but design boundaries so scale can be added later.
